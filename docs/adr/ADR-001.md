# ADR-001: Перенесення бізнес-розрахунків у доменні сутності

## Статус
Прийнято (Accepted)

## Контекст
У вихідному коді класи `Client`, `Vehicle`, `RentalAgreement` були пасивними контейнерами з публічними полями (Anemic Domain Model). Усі розрахунки (вартість оренди залежно від класу авто, страховка, застава за стажем водія, підсумкова ціна) виконувалися в монолітному методі `LegacyRentalManager.processRentalConsole()`. Будь-який код міг змінити поля напряму (`agreement.status = "Approved"`), об'єкти створювалися порожніми й заповнювалися покроково, перевірок валідності не було.

## Розглянуті альтернативи
1. **Залишити розрахунки в сервісі, лише закрити поля геттерами.** Інкапсуляція формально краща, але логіка залишається поза даними.
2. **Винести розрахунки в окремий `PriceCalculator`.** Це Pure Fabrication без потреби, бо потрібні дані вже є в сутностях.
3. **Перенести розрахунки до сутностей-власників даних (обрано).**

## Рішення
Згідно з патерном **GRASP Information Expert**, розрахунки перенесено до сутностей, які володіють потрібними даними: `Client.calculateDeposit()` (стаж водія), `Vehicle.calculateRentalCost(days)` (добова ставка), `RentalAgreement` формує підсумкову вартість (`calculateFinalPrice()`) і керує станом (`approve()`). Усі поля стали `private final`, змінюється лише `status`, і тільки через `approve()`.

## Наслідки
* **Позитивні:**
  * Покращено інкапсуляцію, перейшли до Rich Domain Model.
  * `approve()` перевіряє інваріанти (повторне підтвердження, додатні ціна й застава).
  * Метрики: `Client` CBO 0 → 0, `Vehicle` CBO 0 → 2, `RentalAgreement` CBO 2 → 4, LCOM4 усіх = 1.
* **Негативні / Компроміси:**
  * `RentalAgreement` залежить від `Client`, `Vehicle` та страхової політики (CBO = 4, на межі норми ≤ 4).
